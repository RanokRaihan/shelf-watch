## A1. Any user of any store can write the shared product catalog, and the first save is permanent

- **Severity:** High
- **Where:** `lib/products/products.ts:88`, `actions/scan.action.ts:65`, `components/scan/product-form.tsx:45`
- **Problem:** `Product` is shared by every store, and nothing ever overwrites a row once it exists (`update: {}`). `createProductAction` takes the name, brand, size, `lookupStatus` and `source` from the client. Signup is open, so anyone can create a store and then call the action for any GTIN with any name, marked `FOUND` / `OPEN_FOOD_FACTS`. No UI writes `StoreProduct.name` (the per-store override), and nothing can edit a `Product`, so no store can fix the name.
- **Failure case:** Someone registers a throwaway store and saves made-up or offensive names for popular UPCs. Every real store that scans those items later gets the fake name on its pull list and printed cards, and it is labelled as coming from Open Food Facts. An honest typo by one colleague spreads the same way.
- **Suggested fix:** Set `lookupStatus` and `source` on the server: re-run the provider lookup in `createProduct`, or keep the lookup result server-side, and ignore the client's values. Write what a person types to `StoreProduct.name` (per store), and put only provider data in `Product`. Add a way to edit the store's name for a product.
- **Status:** Open

## A2. No rate limiting on register, join, sign-in or product lookup

- **Severity:** Medium
- **Where:** `actions/register.action.ts:7`, `actions/join.action.ts:8`, `actions/sign-in.action.ts:11`, `actions/scan.action.ts:60`
- **Problem:** No action limits requests by IP or by account. This is a known gap (listed under Must Have in `docs/FEATURES.md`), recorded here so it's tracked. Each register or join also runs one or two bcrypt hashes at cost 12 (about 250 ms of CPU).
- **Failure case:** A script on the wall QR link creates thousands of pending members and buries the Members page. Scripted register calls use up server CPU and fill the database. Repeated lookups can get the server's IP blocked by Open Food Facts (it limits product reads to about 100 a minute), and then lookups fail for every store.
- **Suggested fix:** Add a per-IP limit (and per-token for join) in front of these actions, plus a cap on pending members per store. A small table in Postgres or an edge limiter is enough at this size.
- **Status:** Open

## A3. Manager password can be guessed without limit by re-unlocking with the PIN

- **Severity:** Medium
- **Where:** `lib/auth/manager-access.ts:37`, `lib/auth/unlock.ts:94`
- **Problem:** The 5th wrong password on `/manage/login` ends the session, but a correct PIN starts a new one with the count back at 0. Nothing counts across sessions. The password exists to stop someone who has the manager's phone and PIN, and that person can keep going.
- **Failure case:** A colleague who has seen the manager's 4-digit PIN gets hold of the phone (or copies its `sw_device` cookie). A script loops: unlock with the PIN, try 5 passwords, repeat. That's thousands of guesses an hour, which is enough to break a weak password and get approve, remove and revoke rights.
- **Suggested fix:** Keep the per-session count, and also count `/manage/login` failures per user over a rolling window (for example 20 a day). Past that, require `/sign-in`, or block manager access for a while and show the manager a notice. This keeps the "nobody outside can lock me out" goal, because only someone already holding the PIN session can raise the count.
- **Status:** Open

## A4. Pulled / Skip / Undo fail silently when the network drops

- **Severity:** Medium
- **Where:** `components/pulls/pull-list.tsx:39`
- **Problem:** `mark()` hides the card, then awaits `markPullItemAction` with no `try/catch`. A failed fetch rejects the promise, so the code that un-hides the card and shows an error never runs. `undo()` (line 29) has the same gap.
- **Failure case:** A colleague taps Pulled in a back room with weak Wi-Fi. The card disappears, no toast appears, and the item is still PENDING in the database. They think it's done. It comes back on the next load or shows up as overdue tomorrow.
- **Suggested fix:** Wrap both calls in `try/catch`. On error, un-hide the card and show "Couldn't save. Check your connection." `use-barcode-lookup.ts:62` already does this.
- **Status:** Open
- **Fix notes:**

## A5. No error boundaries, so a server error on a floor page has no retry

- **Severity:** Medium
- **Where:** `app/` (no `error.tsx` or `global-error.tsx` anywhere)
- **Problem:** If a database query in a Server Component throws (a Postgres restart, a pool timeout), Next shows its default error screen. The `Suspense` skeletons cover loading, but nothing covers failure.
- **Failure case:** The database hiccups during a shelf walk. `/pulls` shows "Application error: a server-side exception has occurred", with no button and no way back to the list except reloading.
- **Suggested fix:** Add `app/(app)/error.tsx` (and one for `(auth)`) with a short message and a "Try again" button that calls `reset()` / `router.refresh()`. Also add `app/global-error.tsx`.
- **Status:** Open

## A6. Pull list goes stale after the phone sleeps, including across midnight

- **Severity:** Low
- **Where:** `app/(app)/pulls/layout.tsx:9`. The only `visibilitychange` listener in the app is in `components/scan/use-camera-stream.ts:33`.
- **Problem:** `docs/auth-flow.md` section 3 ("Idle time on the phone") says the client refreshes when the app becomes visible again. That isn't built. A phone that wakes up shows the page as it was last rendered.
- **Failure case:** A phone is left on Today overnight. The next morning it still shows yesterday's list and counts, and the items due today aren't there until someone reloads. Separately, a session that ended while the phone slept only shows up on the next tap.
- **Suggested fix:** Add a small client component in `app/(app)/layout.tsx` that calls `router.refresh()` on `visibilitychange` when the page becomes visible (with a short throttle).
- **Status:** Open

## A7. Device tokens never expire on the server

- **Severity:** Low
- **Where:** `lib/auth/auth-config.ts:13`, `lib/auth/session.ts:124`, `lib/auth/session.ts:213`, `lib/auth/unlock.ts:53`
- **Problem:** The 90-day device lifetime is only the cookie's `maxAge`, which the browser enforces. `Device` has no expiry, and `lastSeenAt` is never checked. A copied `sw_device` value works until a manager revokes it.
- **Failure case:** Someone copies the cookie from a shared or old phone. Months later it still opens the PIN screen for that user. Only a manual revoke stops it, and only if the manager knows about it.
- **Suggested fix:** In `getDevice()`, `getSession()` and `unlockWithPin()`, treat a device whose `lastSeenAt` (or `createdAt` if it was never used) is older than `DEVICE_TTL_MS` as revoked. This needs no schema change.
- **Status:** Open

## A8. Anyone who knows a manager's username can keep them locked out of `/sign-in`

- **Severity:** Low
- **Where:** `lib/auth/sign-in.ts:40`, `lib/auth/sign-in.ts:54`
- **Problem:** The `/sign-in` lockout counts against the User. Five wrong guesses from anywhere lock the account for up to 15 minutes, and repeating it keeps it locked. Usernames are easy to find, because the join and register forms answer "This username is already taken". So the timing-safe "Wrong username or password." message doesn't hide much.
- **Failure case:** A removed colleague keeps the manager locked out of signing in on a new laptop or a replacement phone. The PIN path on their trusted phone still works.
- **Suggested fix:** Fix A2 first (per-IP limits). Then lock per user and IP pair, or show a CAPTCHA, instead of locking the whole account.
- **Status:** Open
- **Fix notes:**

## A9. Duplicate pull item check can be raced

- **Severity:** Low
- **Where:** `lib/pulls/pull-items.ts:62`
- **Problem:** The "same product, expiry and pull date" check is a `findFirst` followed by a `create`, inside a default (read committed) transaction, and no database constraint backs it. The Save button is disabled while submitting, so one phone is covered. Two phones are not.
- **Failure case:** Two colleagues scan the same case at the same time and save the same dates. The list shows the item twice, and marking one leaves the other as a stray overdue item.
- **Suggested fix:** Lock the `StoreProduct` row (`SELECT … FOR UPDATE`) before the duplicate check, as `lockMember` does. A partial unique index needs a schema change, which is Ranok's call.

## A10. Undo is recorded as an `EDITED` pull event

- **Severity:** Low
- **Where:** `lib/pulls/pull-items.ts:232`
- **Problem:** `PullAction` has no `UNDONE` or `REOPENED` value, so an undo is written as `EDITED`. When editing pull items is built, history won't be able to tell "put back on the list" apart from "changed the dates".
- **Failure case:** A manager looks into a missed pull and sees PULLED, then EDITED. They can't tell whether someone undid the pull or changed the date.
- **Suggested fix:** Ask Ranok to add a `REOPENED` action to the enum before item editing ships, then use it here.
- **Status:** Open

## A11. Keyboard-wedge (Bluetooth/USB) scanners don't work on the scan screen

- **Severity:** Low
- **Where:** `components/scan/scanning-screen.tsx`, `components/scan/manual-barcode-form.tsx:54`
- **Problem:** A hardware scanner types the digits and then Enter into whatever has focus. The camera screen has no input and no key listener, so nothing receives them. It only works if the user first opens "Type the number" and taps into the field.
- **Failure case:** A store pairs a Bluetooth ring scanner to speed up a stock check. Scans do nothing until each one is preceded by two taps, which is slower than the camera.
- **Suggested fix:** On the scanning step, listen on `window` for a burst of digit keys ending in Enter (for example 8 to 14 digits within about 100 ms) and pass the result to the same `parseBarcode` path as a typed number.
- **Status:** Open

## Looks solid

- **Authorization:** every action that changes data calls `requireSession()` or `requireManager()`, or `assertGuest()` for the guest-only ones. The store id always comes from the session, and every lookup is scoped by it (`lockMember` and `markPullItem` include `storeId` in their WHERE clause). Associates calling manager actions get redirected, not served. Every page guards itself inside `Suspense`.
- **Secrets:** PINs and passwords are hashed with bcrypt at cost 12. Device and session tokens are 32 random bytes, stored only as sha256. The join token is plain, by design. Session ids never reach the client. `.env` has never been committed, and logs don't include secrets.
- **Sessions:** the 10-hour absolute limit, 30-minute idle timeout, revoke and remove all delete Session rows in the same transaction. Role and status are read from the database on every request.
- **Join links:** rotation revokes every active link under a row lock, and `joinStore` re-checks the link inside its transaction, so an old QR stops working right away.
- **Validation:** every action validates with Zod on the server through `createAction`. Pull dates are validated again in `createPullItem` against the store's today.
- **Dates:** expiry and pull dates are separate optional/required `@db.Date` columns. Pull must be on or before expiry. Offsets use calendar months and never go before today. Today, the buckets and the greeting all use the store's timezone, not the server's.
- **Pull events and names:** a `PullEvent` is written in the same transaction as each create, mark and undo, and `productName` is saved when the item is created.
- **Errors:** unexpected errors are logged on the server and the client only gets a generic "Something went wrong".
- **Camera:** denied, no camera, camera in use, insecure context and an unsupported browser each get their own state. Re-allowing the camera is picked up where the Permissions API supports it. iOS Safari falls back to the self-hosted ZXing WASM, and "Type the number" is always available.
